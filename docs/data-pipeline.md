# Dashboard data pipeline: stage reference

Long-form notes for `npm run populate` (derive → judge → upload → sync-to-kv), moved verbatim from `CLAUDE.md` on 2026-10-06. `CLAUDE.md` § Data Pipeline keeps the rules; this file keeps the reasons and history.

## Stages

- `derive-evaluations.ts` — rule-based metrics (tool_correctness, evaluation_latency, task_completion).
  - **`populate`, and so the schedule, passes `--source=cloud --days=7 --post-days=2`** (`DERIVE_DEFAULT_*` in `pipeline-stages.ts`, cloud-read Phase 1, 2026-09-28).
    - It reads `/v1/traces` over 7 days but posts only the last 2. The wider read keeps session-level records built from whole sessions; posting the whole read would re-send a week each run.
    - The 7 days are also the calibration corpus: `.calibration-state.json` is computed over every record derived. The local default read every trace file (~28 days).
    - Override one run with `--derive-source=local` or `--derive-days=N`. Run directly, derive does the same: cloud, 7 days read, 2 posted (Phase 6, 2026-10-04). `--source=local` is the rollback for one release.
    - A failed cloud read exits `DERIVE_EXIT_READ_FAILED` (9) before anything is posted, and is handled like a failed post.
  - **Every run prints `[derive] records: <name>=<count> …` and checks each day's input for a hooks-side rename** (`detectInputDrift`, HOOK-RENAME-SILENT). It flags a day where spans record agent invocations but none has a name derive matches, and a day where most tool spans lack the success flag derive reads. Either one exits `DERIVE_EXIT_INPUT_DRIFT` (10), which is soft, so the launchd log shows FAILED. The last two renames each looked like a green run for weeks.
  - **Every record is POSTed straight to ingest** (`post-evaluations.ts`), each with an `evaluationId` the worker dedups on. Derive writes no file since Phase 6 (2026-10-04).
    - **It never posts a record dated before 2026-09-28T00:00Z** (`DERIVE_NO_REPOST_BEFORE_MS`), however scoped: D1 holds 45,887 derive rows from 09-16 to 09-27 without an `evaluation_id`, which a re-post would duplicate. The run prints `held back N records` when a scope reaches past it.
    - An unscoped run posts the last two days. `--date=`/`--days=` posts the whole scope, so that is how to backfill, unless `--post-days=N` narrows it.
    - A failed post exits `DERIVE_EXIT_POST_FAILED` (8). `populate` retries derive on a transient network error (the same ~30 min schedule as sync), then carries on to judge, upload and sync. Re-running is safe, and the next run re-posts what was missed.
  - The old `derived-evaluations-<date>.jsonl` files in `TELEMETRY_DIR` are no longer written or read; nothing needs them.
- `judge-evaluations.ts` — LLM-based metrics (relevance, coherence, faithfulness, hallucination). **`faithfulness` and `hallucination` come from one QAG sweep, not two calls**: `judge.qagEvaluateModes(..., ['faithfulness', 'fabrication'])` counts the statements the tool results support and the ones they contradict over the same verification, so the second score is free and **the two do not sum to 1** — a statement the context cannot settle belongs to neither. Until 2026-09-22 `hallucination` was `1 - gEval(faithfulness)`, a separate paid call to a different evaluator that scored every inconclusive statement as a fabrication (`QAG-FABRICATION-MODE-DORMANT`). The consolidated default derives it by inversion — that is its own convention, not this path's. Scores come back schema-constrained: `gEval` sends `output_config` with a JSON schema (`reasoning` before `score`, integer 1-5) and `extractScoreFromText` parses JSON first, falling back to the old regexes for providers that ignore the schema. That closed the failure where ~480 of every 536 calls were billed and produced no score. Key precedence is `LLM_JUDGE_ANTHROPIC_KEY` then `ANTHROPIC_API_KEY` (`judge-credentials.ts`); the `[judge] summary:` line carries real `response.usage` totals, their USD, the pre-run estimate and the key's variable name. Two cost levers, and they combine: **consolidated scoring, the default since 2026-09-22** (`judge-consolidated.ts`, one call per turn; chosen by `judge-quality-eval.ts` against a claude-opus-5 reference, `docs/judge-quality-2026-09-22.json`; `--per-criterion` opts out at ~10x the cost) and `--batch` (`judge-batch-provider.ts`, Message Batches at half price, results settled by `custom_id`, `maxRetries: 0`, ~3 h wall clock with an idle auto-flush), which consolidated rides through `evaluateTurnsConsolidatedBatched`.
  - **Which turns, and where results go** (`judge-selection.ts`, 2026-09-28):
    - Judged, withheld (`null` stamp) and held-for-key turns are dropped before `--limit`, which then takes the oldest pending turns.
    - Records are POSTed straight to ingest (`post-evaluations.ts`) and appended to `evaluations-<today>.jsonl`, the ledger the local source dedups against.
    - The dedup set holds two keys per judged criterion since 2026-10-01: the plain one and one qualified by judge model (`judgedByKey`). The LLM paths check the qualified key, so a second model re-scores what Haiku judged; `--seed` checks the plain one and never seeds a scored turn. Rows written before the model was recorded count as Haiku.
    - A failed post exits `JUDGE_EXIT_POST_FAILED` (6), a soft code, so upload and sync still run. A failed discovery, usually the network under `--source=cloud`, exits `JUDGE_EXIT_DISCOVERY_FAILED` (7), also soft; nothing is spent before it.
  - **Before that, the scheduled judge produced nothing usable from 09-22.**
    - The dedup set was empty, because `otelEvaluationRecordSchema` rejected every post-OBP16 record.
    - The limit sliced before dedup, so each run re-judged the same ~100 turns.
    - Upload's 36 h age guard skipped every judge record as too-old, because a judged turn is weeks old. No judge row reached the cloud after 09-16.
  - **`--source=cloud --days=N`** takes sessions, anchoring and the already-judged set from obtool-api (`judge-cloud-source.ts`, cloud-read Phase 4); turn text stays local.
    - `npm run judge:parity -- --days=7` checks that both sources select the same turns.
    - **`populate`, and so the schedule, passes `--source=cloud --days=7`** (`JUDGE_DEFAULT_*` in `pipeline-stages.ts`), so each run judges turns from the dashboard's default 7-day period and never older ones. Override one run with `--judge-source=local` or `--judge-days=N`.
    - Run directly, the judge does the same: cloud discovery over 7 days (Phase 6, 2026-10-04). `--source=local` is the rollback for one release.
- `upload-evaluations.ts` — ships local `evaluations-*.jsonl` to the **cloud** `evaluations` table over the HMAC webhook. Derive and the judge post their own records, so what it carries is the records only it delivers: `hook:stop-session-summary`, `hook:stop-quality-evaluation` and `survival-fitness` (kept on purpose in Phase 6, `PHASE6-HOOK-EVALUATIONS-UNCOVERED`). **Load-bearing, not plumbing**: the next stage reads the cloud, not these files, so without this every stage reports success and the dashboard still serves `no_data` — which is what happened for five months (`DASHBOARD-PIPELINE-DEAD`). Needs `INJECT_HMAC_SECRET`.
  - A failed send exits `UPLOAD_EXIT_SEND_FAILED` (11), with state saved up to the last accepted batch. `populate` retries a network failure on the same ~30 min schedule as derive and sync, then carries on to sync (UPLOAD-FAILURE-ABORTS-PIPELINE). Until 2026-09-28 it exited 1 and aborted the run, which is how the 18:00 run that day lost its sync.
  - Dedup has two layers. The local content fingerprint skips records already sent, which is what stops a full re-send of the window each run.
  - Every payload also carries `evaluationId(record)`, and the ingest worker drops any id the org already has (migration 0015). That covers a lost or pruned state file.
  - The id keeps `spanId`, and the fingerprint does not. Don't swap one for the other: parallel spans have the same fingerprint but are separate evaluations.
- `sync-to-kv.ts` — delta sync aggregates to Cloudflare KV (priority: meta/agent > metrics > trends > traces)

**The two scoring modes write different producers, and that is the only thing in a stored record that tells them apart.** `dashboard:judge-consolidated` vs `dashboard:judge-evaluations` (`integritystudio.evaluation.producer`, the record's `evaluator` field). They are not interchangeable samples of one series: `faithfulness` is a G-Eval verdict on the consolidated path and a QAG ratio on the per-criterion one, and `hallucination` is that verdict inverted vs a fabrication tally. Everything else on the record — evaluation name, cohort, evaluator kind, judge model — is identical, which is why they were indistinguishable until 2026-09-22 and why the JCP4 cutover would otherwise have been an invisible instrument change mid-series. **Records written before that date all carry `dashboard:judge-evaluations`, whichever path produced them**, so segment on producer *and* date before comparing a judge series across it. Nothing filters or groups on the value today; it exists to be joined on. Since 2026-09-30 the judge model is the second axis a stored record carries: `upload-evaluations` sends it as the webhook's own `judgeModel` field (it was `metadata.judgeModel`, which no reader surfaced) and the parent's `EvaluationResult.judgeModel` is populated from it, so a model change is as visible as a producer change — segment on both.

Full run with its Doppler env: `bash ../scripts/run-dashboard-pipeline.sh`. **A launchd agent does schedule it** — `ai.integritystudio.dashboard-pipeline` fires the wrapper at 06:00 and 18:00 local with `--limit 100` and `--batch` (`~/.local/bin/dashboard-pipeline.sh`, tracked at `../scripts/launchd/`); the long-dead state described by `DASHBOARD-PIPELINE-DEAD` ended when that agent was loaded. `--dry-run` prices a run without spending, and its estimate quotes list rates, so it reads high against a `--batch` run's actuals.

## E2E data skips and the pipeline

- ⚠️ **`npm run populate -- --seed` does NOT lift those skips** (and until 2026-09-15 no invocation of `populate` did). `hasData` is `checkHealth()` in `data-loader.ts`: "did the **cloud API** return ≥1 evaluation in the last 7 days", read through `CloudBackend` over HTTP (there is no local-file backend; an unset `OBTOOL_API_URL` throws). The e2e API reads that cloud table, not KV (which is all `sync-to-kv` writes), so evaluations lift the skips only once they are in the cloud. Until 2026-09-15 nothing carried local evaluations there, and the production dashboard served `no_data` for five months (`DASHBOARD-PIPELINE-DEAD`). Now derive and the judge post their own records (since 2026-09-28, `post-evaluations.ts`) and `upload` carries the hooks' records, so a plain `npm run populate` under `doppler run` does lift the skips. It is not synchronous: rows land via ingest → R2 → the `*/5` flush cron → D1, so allow a few minutes. ⚠️ It writes into **production** telemetry unless scoped to a CI org via `DEV_ORG_ID`. And `--seed` still does not lift them honestly — it produces synthetic scores that `filterCanary` does not drop, so they land in the real aggregates.

## Historical incidents

- **Network outages killed scheduled runs** (until 2026-09-28): the 18:00 firings on 2026-09-17, 18 and 19 all died at sync with no DNS or reset connections on the laptop for fifteen to thirty-five minutes, each leaving `lastSync` a day stale because the stage ran once and gave up. The 2026-09-28 06:00 firing died at derive's post, and the 18:00 firing that day at upload, which gave up after its own four quick attempts and exited 1, aborting the run (UPLOAD-FAILURE-ABORTS-PIPELINE). Derive, upload and sync now wait out a transient failure on `SYNC_RETRY_DELAYS_MS` and carry on.
- **Keyless runs published synthetic judge scores** (until 2026-09-30): `populate` fell back to `--seed` when `ANTHROPIC_API_KEY` was absent — first silently (an empty block), then with a warning — so a run that lost its key filled the dashboard with plausible numbers while every stage reported success. No evaluator vendor surveyed does this; they fail visibly (Langfuse marks the run Error, LangSmith pauses the evaluator). The check also read `ANTHROPIC_API_KEY` alone and treated a run with only `LLM_JUDGE_ANTHROPIC_KEY` set as keyless. `populate` now fails closed through `resolveJudgeApiKey`.
- **The judge reported failure as success** (2026-09-16 to 09-19): every scheduled run attempted evaluations and produced none while the launchd log said "completed". One oversized tool result failed every metric for its turn with "Invalid TestCase … too_big" — 60 of the 480 failures in each run — until `fitContextForJudge` capped the context. The dry-run's estimate was also the only cost figure a run reported ($1.80 estimated against ~$3.30 billed) until the summary line carried real `usage`.
- **Records mixed kind and cohort** (until OBP16): `createEvalRecord` took `(evaluator, evaluatorType)`, and callers passed a value that was sometimes a kind and sometimes a cohort, so a hashed canary score was written as `evaluator: 'llm'`, indistinguishable from a judged one; the trace backfill overwrote a kind with a cohort value.
- **A `--batch` wall-clock overrun aborted the run** (until 2026-10-05): it exited 1, costing the 06:00 runs on 09-29 and 09-30 their upload and sync. It is now the soft `JUDGE_EXIT_BATCH_WALL_CLOCK` (12) (JUDGE-BATCH-WALLCLOCK-ABORTS-RUN).
- **Soft failures logged "completed"**: before the judge and derive soft codes were forwarded to `populate`'s own exit, the launchd wrapper logged "completed" for runs that produced no judge scores, and the last two hooks-side renames went unnoticed for weeks (HOOK-RENAME-SILENT).
- `GET /api/agents` returned 500 on **every** request until 2026-09-14 (PR #6): `queryTraces` types its date bounds `string | bigint` but validates the string arm as an ISO *datetime*, so the route's date-only `'YYYY-MM-DD'` type-checked and failed Zod. Fixed there and in the sessions route via `toIsoWindowBound`.
